## Step 1 — Architecture security assessment

### 1. `/attest/submit`: challenge, identity and replay controls

The current attestation endpoint is not just a client-supplied hardware report. The route at `node/rustchain_v2_integrated_v2.2.1_rip200.py` around lines 6120–6650 first validates that the request is a JSON object and that the payload shape is acceptable. It normalizes the miner identity, report, nonce and device fields before moving into authentication. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L6120-L6650

The signature path supports the current full canonical-JSON Ed25519 scheme and an older four-field compatibility MAC. For the current scheme, the node reconstructs the canonical JSON after removing `signature`, `signature_type`, and `public_key`, then verifies the Ed25519 signature. A request explicitly declaring the stronger `ed25519`/`canonical_json` type is not allowed to fall through to the narrower legacy verification. The same section rejects malformed partial signature/public-key pairs and, in enforcing phases, fails closed when miner identity state cannot be read. A verified key is then checked against pinned identity state; self-certifying `RTC…` identities require the public key to derive to the address, while legacy/grandfathered identities are deliberately not trust-on-first-use pinned without the safer conditions described in the code.

Freshness is enforced separately from signature validity. The endpoint requires a nonce and calls `attest_validate_and_store_nonce()` around lines 6430–6475. The result distinguishes missing/expired/already-used challenges, nonce replay, and identity mismatch. The project whitepaper documents `/attest/challenge` as returning a nonce with an expiry, and the regression tests bind challenge nonces to the intended miner identity. This prevents a valid signature over stale or borrowed challenge material from automatically becoming a fresh attestation.

After nonce validation, the node applies wallet-review gating, hardware binding, OUI checks, and fingerprint replay defenses. The hardware-binding section around lines 6500+ prefers `hardware_binding_v2` when a serial is available and falls back to a legacy binding check that itself fails closed on database errors. The replay-defense block computes fingerprint and entropy hashes, checks fingerprint replay, entropy collisions and per-hardware rate limits, and records accepted submissions for future comparison. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L6500-L6650

### 2. Hardware fingerprinting and VM-farm resistance

RustChain does not rely on one boolean such as `is_vm`. The current RIP-309 path rotates among six signals: clock drift, cache timing, SIMD identity/bias, thermal drift, instruction jitter and anti-emulation. `select_active_fingerprint_checks()` around lines 2420–2440 normally chooses a deterministic subset from the previous epoch block hash, but importantly activates all checks when that hash is unavailable or falls back to the all-zero seed. That is a fail-closed choice: early-epoch or read-failure conditions do not turn two checks into predictable optional checks. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L2420-L2445

The check parser itself is also hardened. `_fingerprint_check_passed()` around lines 2580–2595 requires an explicit boolean `True`; missing `passed`, empty dictionaries, and truthy strings such as `"false"` do not count as a pass. This specifically closes a fail-open shape where a VM could formerly submit empty check dictionaries. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L2580-L2598

The design also avoids unfairly treating structurally incapable vintage systems as ordinary failed modern systems. Capability-limited architectures use server-derived architecture classification and must supply native evidence before structurally unmeasurable checks are removed from the denominator. That matters because trusting the client's requested architecture would itself be an evasion path. Elsewhere the node checks server-visible VM signatures in host/CPU fields and cross-validates architecture claims. Measurement freshness is further bound to the challenge nonce by deriving a workload from it, which makes replaying old timing content detectable even when wrapped in a newly issued envelope.

### 3. Epoch rewards and settlement

`finalize_epoch()` begins around lines 5454+ and treats reward settlement as state transition rather than a blind balance update. It checks `epoch_state` for an already-settled epoch, loads the enrolled miners and normalized weights, records explicit unsettled reasons when there are no miners/zero total weight, uses `Decimal` for reward arithmetic, and clamps the emission budget to remaining supply headroom. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L5450-L5535

Miners already carrying zero weight are excluded as VM/emulator failures. The settlement path then re-evaluates the epoch's active RIP-309 checks and can zero a miner before payout. Later in the function, settlement is claimed under `BEGIN IMMEDIATE` with an atomic `settled = 0 -> 1` update before crediting, so the early read is not the authoritative double-settlement defense. This is important because two workers can race past a pre-check; the write-locked claim is what prevents duplicate credits.

### 4. Potential residual attack surface: fail-open missing checks in `finalize_epoch`

One inconsistency deserves a regression test. In the primary fingerprint parser, a missing or malformed active check fails closed: `_fingerprint_check_passed()` requires explicit `True`. But the reward-time re-check around lines 5530–5555 reconstructs `checks_map` from `miner_attest_recent.fingerprint_checks_json` and uses:

```python
active_passed = all(checks_map.get(chk, True) for chk in active_checks)
```

Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L5530-L5558

That expression treats a missing key as passing at settlement time. I am **not** claiming a confirmed reward-bypass from this review alone: the earlier attestation/enrollment gates may ensure that a positive-weight miner cannot reach this point with a partial stored check map. The security concern is the semantic mismatch itself. If migration, legacy records, partial JSON, or another writer can create a positive-weight enrolled miner whose stored map omits an active key, settlement interprets absence as success even though the main validator interprets absence as failure. The right next test is to construct exactly that state locally and assert that `finalize_epoch()` zeros the miner. If the state is impossible by invariant, that invariant should be encoded in a test; otherwise this should use an explicit-fail helper rather than `get(..., True)`.

This is a potential attack surface, not a Step-3 vulnerability claim.

## Step 2 — Reproduce a known fix: Mock Signature Mode

### What the old failure mode was

Historical RustChain node backups show that the test flags were once controlled directly by environment variables:

```python
TESTNET_ALLOW_INLINE_PUBKEY = os.environ.get("RC_TESTNET_ALLOW_INLINE_PUBKEY","0") == "1"
TESTNET_ALLOW_MOCK_SIG      = os.environ.get("RC_TESTNET_ALLOW_MOCK_SIG","0") == "1"
```

Example source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/deprecated/node_backups/rustchain_v2_integrated_v2.2.1_rip200.backup_20251004_084811.py#L20-L27

The dangerous configuration class is straightforward: a production process inheriting `RC_TESTNET_ALLOW_MOCK_SIG=1` could enable a test-only authentication relaxation in the same binary that handles real attestations. The problem is not that an attacker can set the server's environment remotely; the problem is that a production security boundary depended on deployment hygiene rather than a fail-closed runtime invariant.

### Current fix in the code

The current integrated node hardcodes both test switches to `False` and defines `_MOCK_SIG_ALLOWED_ENVS`. `enforce_mock_signature_runtime_guard()` raises when mock signatures are enabled while `RC_RUNTIME_ENV`/`RUSTCHAIN_ENV` is not a recognized test/development environment. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/rustchain_v2_integrated_v2.2.1_rip200.py#L110-L125

The production WSGI entry point then calls the guard immediately after loading the main module and **before** `init_db()` or serving the Flask application:

https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/wsgi.py#L15-L31

The upstream regression test `node/tests/test_mock_signature_guard.py` checks all three important behaviors: production + mock enabled raises, test runtime + mock enabled is allowed, and WSGI startup invokes the guard before database initialization. Source: https://github.com/Scottcjn/Rustchain/blob/217ba85ef9cab3daac0da7b822c79437693444df/node/tests/test_mock_signature_guard.py#L29-L75

### Local reproduction

I reproduced the guard's exact control flow in an isolated dependency-free script so the test does not require importing the full Flask node and optional native modules:

https://github.com/fsalmon1991/Python/blob/main/submissions/rustchain-security-quest/repro_mock_signature_guard.py

Observed output:

```text
runtime_env='production' mock_enabled=True -> BLOCKED: TESTNET_ALLOW_MOCK_SIG must not be enabled outside test/dev runtimes
runtime_env='test' mock_enabled=True -> ALLOWED
runtime_env='production' mock_enabled=False -> ALLOWED
```

The three cases establish the intended boundary: the dangerous combination is blocked, controlled test usage still works, and ordinary production stays unaffected.

### Why the fix is sufficient — and its boundary

For the documented Gunicorn production path, the fix is strong because it combines three layers: the production constant defaults to disabled; a runtime assertion forbids an accidental enabled state outside dev/test; and `wsgi.py` executes that assertion during startup before the app is initialized. The upstream regression test protects that ordering.

The residual operational boundary is entry-point coverage. A future production launcher that imports the module but bypasses `wsgi.py` would need to call the same runtime guard before serving requests. That is not evidence of a current bypass; it is the condition that should remain part of deployment review. The current WSGI path satisfies it.
